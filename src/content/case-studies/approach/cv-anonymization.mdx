The pipeline has two halves that are deliberately kept apart, and the separation is the whole
design.

### Understanding, then removal

A CV is a layout problem before it is a text problem. The same name appears as a heading, inside
an email address, in the file name, in a footer on every page, and in a sentence about a previous
employer. A rules-only parser handles the predictable cases and misses the rest, because there
are more layouts than anyone is going to enumerate.

So the model reads the document and reports what it found and where. It does not edit anything.

Removal is then done by deterministic code against those locations. That ordering matters more
than it looks. If the model performed the redaction, the output would be probabilistic: mostly
right, occasionally wrong in a way nobody can predict, and impossible to audit afterwards. With
the split, every removal is a rule applied to a location, so it can be explained, repeated, and
checked.

### Confidence, and the person at the end

The claim is assisted automation, not autonomy, and the pipeline is built so that stays true.
Extraction carries a confidence signal, and low confidence routes the document to a person
rather than through to output. The failure mode is designed to be a delay, not a leak.

That choice is what makes the whole thing defensible in a domain where being nearly right is
the same as being wrong.

### The alternative I rejected

The obvious design is to hand the model the document and ask for a redacted one back. It is
faster to build and it demonstrates well.

I rejected it because you cannot audit the result. If an agency is asked why a particular
detail was removed, or worse, why one was not, the answer under that design is a shrug. Under
this one it is a rule and a location. For a task where a single miss defeats the exercise, that
difference is the product.

### Data handling

Candidate CVs are personal data, so retention, access and where processing happens are part of
the design rather than an operational detail bolted on afterwards. The general principle: hold
documents for as long as the work requires and no longer, and keep the processing boundary
somewhere you can describe to a client without hedging.
