### The Go service and its OpenAPI contract

The API is public, which changes how you build it. An internal endpoint can be reshaped the
afternoon somebody needs it reshaped. A documented one that third parties integrate against
cannot, because breaking it breaks somebody else's system without warning them.

So the contract came first. The OpenAPI specification is what the front end and any external
integrator build against, and the Go implementation is held to it rather than the other way
round. That ordering costs a little at the start and saves the argument about what the API
actually does every time after.

The documentation route is public, which means the claim is checkable rather than asserted.

### Keeping the specification honest

A specification that drifts from the implementation is worse than none, because people trust
it. The failure is quiet: an endpoint changes, the document does not, and an integrator
discovers the difference in production.

The defence is to stop treating the specification as a document that describes the code and
start treating it as the thing the code is checked against — generated from and validated
against the implementation rather than maintained beside it.

### Barcodes and the warehouse workflow

Warehouse work is where a shipping platform stops being software. Barcode generation and the
data processing around it existed to remove the step where a person reads a number off a screen
and types it somewhere else, which is the step that produces mis-shipments.

### The Apps Script build pipeline

This is the part I would want to talk about in an interview.

Google Apps Script is a genuinely odd deployment target. It expects you to write JavaScript in
a browser editor and press save. There is no bundler, no module system worth the name, no
version, and no notion of a release. That is tolerable for a script one person wrote once, and
untenable for automation a business depends on.

So the source is TypeScript, in a normal repository, with a normal review process. It is
compiled and bundled into the shape Apps Script will accept, then deployed as a versioned
release rather than pasted. The result is that Workspace automation gets the same properties as
the rest of the codebase: you can see what changed, you can tell which version is running, and
you can put back the one that worked.

The alternative was to accept the platform's model and maintain the automation in the web
editor. Rejected because it makes review impossible and rollback a matter of memory. The cost
of the toolchain is real, and it is paid once.
